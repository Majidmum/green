# GREEN GARDEN

Интернет-магазин свежих фруктов и овощей (Душанбе, TJS) с тремя интерфейсами — клиентским магазином, панелью администратора и панелью руководителя. Стек: Next.js 14 (App Router, JavaScript/JSX), Tailwind CSS, Supabase (PostgreSQL, Auth, Storage, Realtime, RLS).

**Что уже работает (этапы 3–4):** главная, каталог (поиск, категории с подкатегориями, цена, наличие, скидки, популярность, сортировка, пагинация, плитка/список), категории, карточка товара, отзывы (просмотр), регистрация, вход, восстановление пароля, О нас, Контакты, FAQ, юридические страницы, sitemap/robots, 404/500. Кнопки «В корзину» и «В избранное» работают. **Этап 4:** корзина (сверка цен и остатков с БД при каждом открытии, предупреждения об изменениях), промокоды, оформление заказа (доставка/самовывоз, район, сохранённый или новый адрес, дата и время, контакты, оплата наличными), защита от двойной отправки (ключ идемпотентности), списание остатков и номер заказа GG-ГГММДД-NNNNN, страница «Заказ принят». Онлайн-оплата — заглушка «Скоро». Необязательное уведомление в Telegram: задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.

**Пока ведут на 404 (будут на этапах 4–7):** `/profile`, `/orders`, `/favorites`, `/admin/*`, `/manager/*`. Страница «Мои заказы» появится на этапе 5 (после заказа кнопка ведёт на `/orders`).

**Настройка Auth для регистрации:** в Supabase → Authentication → Providers → Email по умолчанию включено подтверждение email. Для быстрых тестов можно отключить «Confirm email»; в продакшене лучше оставить включённым.

## 1. Установка проекта

Требуется Node.js 18.18+ (рекомендуется 20 LTS) и аккаунт [Supabase](https://supabase.com).

```bash
cd green-garden
```

## 2. Установка зависимостей

```bash
npm install
```

## 3. Создание проекта Supabase

1. На supabase.com создайте проект (регион — ближайший к пользователям, например Frankfurt).
2. Сохраните пароль базы данных.
3. Откройте **Project Settings → API** и скопируйте: `Project URL`, `anon public` ключ и `service_role` ключ.

## 4. Переменные окружения

```bash
cp .env.example .env.local
```

Заполните `.env.local`:

| Переменная | Назначение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL проекта |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | публичный ключ (доступ ограничивает RLS) |
| `SUPABASE_SERVICE_ROLE_KEY` | **секрет**, только сервер, обходит RLS |
| `NEXT_PUBLIC_SITE_URL` | адрес сайта (sitemap, Open Graph, письма) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | необязательно: уведомления о заказах |

> `SUPABASE_SERVICE_ROLE_KEY` не должен иметь префикс `NEXT_PUBLIC_` и импортируется только в `lib/supabase/admin.js` (файл защищён `server-only` — сборка упадёт, если его импортировать в клиентский компонент).

## 5. Выполнение SQL-миграций

Откройте **SQL Editor** в Supabase и выполните файлы из `supabase/migrations/` **строго по порядку**:

1. `20250101000001_schema.sql` — типы, 23 таблицы (21 обязательная + `banners` и `order_returns`), индексы
2. `20250101000002_helpers_triggers.sql` — роли, аудит, уведомления, триггеры
3. `20250101000003_inventory_rpc.sql` — приход, списание, инвентаризация
4. `20250101000004_orders_rpc.sql` — цены, промокоды, заказы, возвраты
5. `20250101000005_rls_storage_realtime.sql` — RLS, представления, Storage, Realtime

Либо через Supabase CLI: `supabase link --project-ref <ref>` и `supabase db push`.

Затем выполните `supabase/seed.sql` — тестовые категории, 28 товаров, начальный приход, районы доставки, промокод `WELCOME10`, акция «Ягодная неделя». Цены и тарифы **тестовые**. Seed можно запускать повторно.

## 6. Настройка Storage

Бакеты создаются миграцией 005: `product-images`, `banners` (загрузка — только администратор), `review-photos` (пользователь пишет только в папку `{user_id}/`). Лимиты: 5 МБ / 3 МБ, форматы JPEG, PNG, WebP. Проверьте в **Storage**, что три бакета есть.

Проверьте также **Database → Publications → supabase_realtime**: в списке должны быть `orders`, `notifications`, `order_status_history`.

В **Authentication → URL Configuration** укажите Site URL и добавьте в Redirect URLs `http://localhost:3000/**` и адрес продакшена — это нужно для восстановления пароля.

## 7. Создание первого администратора

Роль `admin` нельзя получить через регистрацию или API — только SQL-запросом владельца базы.

1. Зарегистрируйтесь на сайте (или **Authentication → Users → Add user**).
2. В SQL Editor выполните:

```sql
update public.profiles set role = 'admin' where email = 'admin@example.com';
```

Дальнейшие роли администратор выдаёт в разделе «Управление пользователями» (RPC `admin_set_user_role`).

## 8. Создание первого руководителя

```sql
update public.profiles set role = 'manager' where email = 'manager@example.com';
```

Руководитель видит все данные (заказы, склад, журналы, расходы, аудит), но **ничего не может изменить**: ни остатки, ни заказы, ни финансы.

## 9. Запуск локального проекта

```bash
npm run dev          # http://localhost:3000
npm run test:db      # проверка миграций, seed, RLS и RPC на локальном PostgreSQL
```

## 10. Деплой на Vercel

1. Загрузите репозиторий на GitHub и импортируйте проект в Vercel.
2. В **Settings → Environment Variables** добавьте переменные из `.env.example` (service role — только для окружения Production/Preview, не публичная).
3. `NEXT_PUBLIC_SITE_URL` — боевой домен; тот же домен добавьте в Redirect URLs Supabase.
4. Deploy.

## Как устроены склад и деньги

* **Остаток** (`inventory`) меняется только функциями БД; прямой `UPDATE` запрещён для всех ролей. Каждое изменение пишется в **неизменяемый журнал** `inventory_transactions` (UPDATE/DELETE блокирует триггер даже для владельца базы). Остаток всегда равен сумме движений — это проверяется тестом.
* Типы движений: `purchase`, `sale`, `sale_cancel`, `write_off`, `supplier_return`, `customer_return`, `adjustment`.
* Остаток списывается **в момент оформления заказа** и возвращается при отмене. Двойное списание и двойной возврат исключены уникальным индексом и блокировкой строки заказа.
* Отрицательный остаток невозможен (`CHECK` + проверка в функции). Параллельные заказы на последний товар сериализуются блокировкой `FOR UPDATE`.
* Себестоимость — средневзвешенная; в позиции заказа сохраняется её снимок, поэтому прибыль считается корректно даже после смены закупочных цен.
* Приходный документ нельзя ввести дважды (уникальность «поставщик + номер документа + товар»).
* Инвентаризация сверяет остаток, который видел сотрудник, с текущим; если за время подсчёта прошла продажа — операция отклоняется.

**Правила расчёта для панели руководителя (этап 7):**
выручка = сумма `total` доставленных заказов − возвраты; себестоимость = Σ `unit_cost × quantity` проданных позиций, за вычетом возвращённых на склад; валовая прибыль = выручка − себестоимость; чистая прибыль = валовая прибыль − операционные расходы (`expenses`, кроме аннулированных) − списания по причинам порчи/потерь. Возврат поставщику не считается потерей. Выручка, остатки и прибыль считаются отдельными запросами и не смешиваются.

## Безопасность

* Все таблицы под RLS; у `anon` доступны только витрина, публичные настройки, активные акции, баннеры и зоны доставки.
* Заказы, склад, журналы, уведомления клиент не может писать напрямую (права отозваны на уровне таблиц **и** нет политик) — только через RPC, которые сами проверяют роль и пересчитывают цены, остатки, промокод и доставку на сервере.
* Профиль: клиент может менять только имя, телефон и аватар (column-level GRANT + триггер-защита от смены роли).
* Заблокированный пользователь (`is_active = false`) не может менять данные и создавать заказы. Чтобы дополнительно закрыть вход, серверный код при блокировке должен вызвать Auth Admin API (`ban_duration`) с service role — это будет сделано в разделе «Управление пользователями».
* Закупочные цены клиентам недоступны: витрина `product_catalog` отдаёт только публичные поля и остаток.
* Расходы нельзя удалить (только аннулировать); изменения расходов, цен, промокодов, акций, настроек, ролей пишутся в `audit_logs` с автором.
* Покупатель может оставить отзыв только на товар из своего доставленного заказа; правка отзыва возвращает его на модерацию.
* Повторное оформление: уникальный `idempotency_key` на пользователя.

## Что проверено автоматически

`npm run test:db` поднимает PostgreSQL (PGlite), прогоняет все миграции и seed и выполняет 133 проверки: права каждой роли, изоляция клиентов, атомарность заказа и отмены, промокоды, акции, склад, инвентаризация, возвраты, журналы, отзывы, Storage-политики, идемпотентность seed.

**Не покрыто тестами:** реальные параллельные запросы (PGlite — одно соединение; защита построена на `FOR UPDATE` и уникальных индексах, но нагрузочно не проверялась) и поведение самого Supabase (Auth, Realtime). Эти части нужно проверить на вашем проекте.

## Юридические страницы

Тексты `/offer`, `/privacy-policy`, `/terms`, `/delivery` хранятся в `store_settings` (`page:*`) и редактируются из админ-панели. В seed — только плейсхолдеры `[ЗАПОЛНИТЬ]`: реквизиты и условия не придуманы, их нужно заполнить и согласовать с юристом.

## Этапы 5–7: кабинет клиента, админка, руководитель

**Миграция:** примените `supabase/migrations/20250101000006_reports_admin.sql` в SQL Editor Supabase.

**Маршруты**
- Клиент: `/profile`, `/orders`, `/orders/[id]`, `/favorites`, `/my-reviews`
- Админ: `/admin` (дашборд, заказы, товары, склад, поставщики, акции, промокоды, баннеры, зоны доставки, расходы, отзывы, клиенты, пользователи, настройки, аудит, отчёты)
- Руководитель (только чтение): `/manager` (дашборд, финансы, заказы, склад, клиенты, персонал, аудит, отчёты)

**Первый админ / руководитель:** зарегистрируйтесь на сайте, затем в SQL Editor:
`update public.profiles set role = 'admin' where id = (select id from auth.users where email = 'ваш@email');` (для руководителя — `'manager'`). Дальше роли меняются в `/admin/users`.

**Формулы:** выручка = сумма доставленных заказов − возвраты; себестоимость = закупочная цена × количество; валовая = выручка − себестоимость; чистая = валовая − расходы − списания. Стоимость остатков в прибыль не входит. Даты — по Душанбе (UTC+5).

**PDF:** кнопка «Печать / PDF» открывает печатную форму браузера. Excel-отчёт: `/api/reports/export`.

## Тёмная тема и главная

- Тема: переключатель (солнце/луна) в шапке сайта и админки. Выбор хранится в браузере, без выбора берётся тема системы. Цвета заданы переменными в `app/globals.css` (`--page`, `--surface`, `--tint`, `--heading`, `--body`) и классами `bg-page`, `bg-surface`, `bg-tint`, `text-heading`, `text-body`. Графики берут цвета из `--c-*`. Печать всегда светлая.
- Главная: баннер, карточки сервисов, цифры (товары, категории, зоны доставки из базы), акции, товары, отзывы, доставка, контакты (из настроек `store_info`).

**Блоки сервисов на главной (миграция 7).** Выполните `supabase/migrations/20250101000007_home_services.sql` в SQL Editor. Затем в админке: «Маркетинг → Блоки сервисов» — загрузите фото и поправьте тексты карточек.

**Фото сервисов (миграция 8).** Фото лежат в `public/services/`. Выполните `supabase/migrations/20250101000008_home_services_photos.sql`, чтобы привязать их к карточкам. Заменить фото можно в админке («Маркетинг → Блоки сервисов»).
